# 0.2.9 연속 삭제 뒤 입력 순서

0.2.8에서 남겨 둔 문제를 수정했다. `ㄹㄹㄹㄹㄹ`을 모두 지운 직후 `tlu`로 `싫`을 입력하면, 마지막 Backspace가 새 `ㅅ`의 삽입보다 늦게 처리되어 `ㄹㅣㅕ`처럼 남을 수 있었다.

## 변경

두꺼비가 연속해서 쓴 일반 텍스트를 지울 때, 원래 Backspace를 앱에 넘기는 대신 `setMarkedText("", selectionRange: 0, replacementRange: 삭제할 범위)`를 보낸다. 이 경로는 `insertText("")`를 무시하던 입력창에서도 삭제를 수행하며, 다음 문자 삽입과 같은 문자 전달 경로를 쓴다. 삭제 뒤 별도의 확정 요청을 보내거나 조합 표시를 유지하지 않는다.

마지막 조합 자모뿐 아니라 같은 입력에서 이미 확정한 자음도 한 글자씩 지운다. 현재 조합의 `각 → 가 → ㄱ`, `싫 → 시 → ㅅ` 처리는 유지한다.

삭제 전에는 입력창, 커서, 실제 글자가 일치하는지 확인한다. 입력 도중 쓴 글자는 해당 입력 세션의 메모리에만 두며 파일이나 네트워크에 기록하지 않는다. 공백·방향키·단축키·클릭·확정·입력창 변경이 생기면 비운다. 이전 글자나 목록·줄바꿈에 관한 앱의 편집 명령은 앱에 맡긴다. 타이머, 키 입력 대기, 앱별 예외는 추가하지 않았다.

## 설치된 입력기를 거친 검사

전용 InputProbe의 WKWebView + CodeMirror에 CUA `pressKey`로 고정된 키를 보냈다. 삭제와 다음 자모 사이에는 화면 확인이나 대기 시간을 넣지 않았다. 일반 모드와 Vim 입력 모드에서 각각 6회, 총 12회 실행했다.

모든 실행에서 아래 **중간 상태 전체**가 순서대로 일치했다.

1. `ㄹ → ㄹㄹ → ㄹㄹㄹ → ㄹㄹㄹㄹ → ㄹㄹㄹㄹㄹ`
2. Backspace 5회로 한 글자씩 줄어 빈 목록 항목이 됨
3. `ㅅ → 시 → 싫`
4. Backspace 3회로 `시 → ㅅ → 빈 목록 항목`
5. `ㄱ → 가`, Enter 뒤 `- 가\n- `

모든 문서 변경 시점에 편집기의 `composing`은 false였다. 검사 기록은 [시스템 입력 기록](verification/0.2.9-system-bursts.json)에 있다. 사용자 SilverBullet 문서는 수정하지 않았다.

시스템 검사 이후 최종 소스에서는 입력 추적의 256자 제한을 없애고, 삭제 전 확인을 다음에 지울 한 글자로 줄였다. 아래 자동 검사는 그 최종 소스를 대상으로 한다. 시스템 검사는 SilverBullet의 모든 확장이나 다른 모든 앱의 동작을 보증하지 않는다.

## 자동 검사

**17,077개 검사, 실패 0개.** 실제 NSTextView를 쓰는 검사에 마지막 네이티브 Backspace를 다음 IMK 삽입 뒤까지 미루는 조건을 추가했다. 이는 WebKit 기록에서 관찰한 순서를 재현한다.

같은 검사를 0.2.8의 InputSession에 적용하면 28개가 실패했다. 특히 삭제 직후 `싫`을 입력하는 12개 조건 모두 `ㄹㅣㅕ`로 남아, 새 검사가 이전 문제를 잡는 것을 확인했다. [구버전 실패 기록](verification/0.2.9-regression-before.txt).

- 1·5·30·257개의 반복 자음을 삭제하고 즉시 `싫` 입력
- 빈 문서, 목록 표식, 이모지 뒤에서 같은 검사
- 커서·선택 영역·문서·입력창 변경 및 확정 뒤의 삭제 권한 해제
- 앞부분만 앱이 바꾼 경우, 그 글자를 두꺼비가 지우지 않는지 확인
- 삭제 뒤 조합 표시, Enter 추가 삽입, 실행 취소·다시 실행 검사
- 기존 현대 한글 11,172자, 겹받침, 대체 시프트, 붙여넣기 검사
