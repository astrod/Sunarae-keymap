# Sunarae 0.5.3 (22) — 2026-10-09

## 보고와 원인 조사

사용자가 Ghostty의 자모 분리와, 여러 앱에서 간헐적으로 `설계`가 `서ㄹ계`로 나오는
문제를 보고했다. 설치본은 `0.5.2 (21)`이었다.

설치된 Ghostty는 `56a3437a7` / 빌드 `17893`이다.
[해당 커밋의 NSTextInputClient 구현](https://github.com/ghostty-org/ghostty/blob/56a3437a7f51796d7946584043229c2f15c70583/macos/Sources/Ghostty/Surface%20View/SurfaceView_AppKit.swift#L1921)은
터미널 선택 영역을 조회하고 `insertText`의 `replacementRange`를 쓰지 않는다.
일반 문서처럼 확정한 자모를 다시 교체할 수 있다는 순아래의 판단이 잘못됐다.
같은 응답을 내는 검사 클라이언트에서 수정 전 `설계 → ㅅㅓㄹㄱㅕㅣ`를 재현했다.

빠른 입력 시험에서는 `설계 서rㅖ` 같은 깨짐을 확인했다. 이벤트 기록에 다음 `r`의
일반 keydown과 삽입이 앞선 `f`의 IME keydown보다 먼저 나타났다.
코드에는 글자 조회·쓰기 도중 들어온 다음 키를 `false`로 돌려보내는 부분이 있었다.
이를 고치는 도중 공백도 기다리는 한글 키보다 앞서면 글자가 다시 깨짐을 확인했다.
사용자가 본 `서ㄹ계`의 모든 발생 원인을 확정한 것은 아니다.

## 수정

- Ghostty의 번들 ID에서는 표준 조합 표시를 쓴다. 확정한 자모를 되돌려 교체하지 않고
  조합을 마친 글자를 터미널에 보낸다. Ghostty의 기본 조합 표시가 보일 수 있다.
- 글자 조회·쓰기 중 다시 들어온 한글 키와 일반 공백을 잠시 보관하고 도착 순서대로 처리한다.
  각 키의 Shift 상태와 원래 클라이언트를 보존한다. 타이머나 합성 키 이벤트를 쓰지 않는다.
- ABC 전환 도중 들어오는 키는 기다리는 한글 키에 넣지 않는다. Enter·수정키·Vim 일반 모드의
  원래 키 이벤트 처리를 유지한다. 다른 편집기는 기존의 조합 표시 없는 방식을 유지한다.
- 입력기를 추적하거나 입력 내용을 기록하는 코드는 추가하지 않았다.

## 실제 키 시험

사용자 입력이 시험창에 들어온 때는 시험을 중단했다. 사용자가 다시 허락한 뒤 진행한
고정 예문의 결과만 집계했다. 섞인 사용자 입력 구간은 보관한 시험 기록에서 제외했다.

- 일반 웹 20회·Vim 삽입 모드 20회, 매회 `tjfrul tjfrP `와 Return 입력.
  총 80번의 `설계`가 맞았고 40회 모두 `- 설계 설계\n- `로 목록이 이어졌다.
- 위 시험에서 조합 이벤트 0개. Enter 40개 모두 `keyCode=13`, `isComposing=false`,
  편집기 `composing=false`였다.
- Vim 삽입 모드: `ㄹ` 다섯 개 삭제 직후 `까`, Backspace로 `가`, Enter로 목록 잇기 확인.
  화면에서 마지막 글자가 선택된 것처럼 보이지 않았다.
- 네이티브: 입력 연결이 자리 잡은 뒤 `설계`와 Enter 줄바꿈 확인.
- 재설치 직후에는 영문이 나오거나 첫 빠른 입력의 Enter가 반영되지 않는 경우가 있었다.
  기본 두벌식·순아래 재선택 뒤의 입력 및 최종 줄바꿈 확인과 구분한다.
- 시험창은 종료했고 시험 전의 ABC 선택을 복원했다. 입력기 프로세스는 설치 경로에서 실행 중이다.

Ghostty 실제 창 제어는 자동 승인 검토가 “안전상의 이유”로 차단했다.
다른 경로로 우회하지 않았다. Ghostty 소스에 맞춘 검사와 자동화한 실제 앱 시험을 구분한다.
2026-10-09 사용자가 설치본의 입력이 잘 된다고 확인하고 릴리즈를 요청했다.
사용자가 확인한 세부 앱·예문·횟수는 따로 보고받지 않았다. 모든 앱에서 간헐적 오류가 사라졌다고 단정하지 않는다.

배포 버전은 0.5.3, 빌드 번호는 22다. Apple Silicon용 설치 파일과 해당 커밋의 소스 ZIP,
