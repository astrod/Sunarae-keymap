## 실제 키 입력

사용자 허락을 받아 별도 시험창에 고정 예문만 키로 입력했다. 붙여넣기로 대신하지 않았다.

- 네이티브: `rkk → 까`, `까 → 가 → ㄱ → 빈칸` 삭제, `까 각 과 예` 입력 확인.
- 마지막 글자에 선택 표시가 없음을 화면으로 확인했다. 네이티브 기록의 선택 길이와 조합 범위 길이는 0이었다.
- 일반 웹: `까 각 과 예` 입력과 Enter 한 번으로 다음 목록 항목 생성 확인.
- 일반 웹 및 Vim 삽입 모드: `ㄹ` 다섯 개를 지운 직후 `rkk → 까`, Backspace로 `가` 확인.
- 웹 Enter 이벤트는 `keyCode=13`, `isComposing=false`, 편집기 `composing=false`였다.
- 최종 설치 뒤 다시 `rkk → 까`와 네이티브 줄바꿈, 웹 `어렵다`와 Enter 목록 잇기를 확인했다.

재설치 직후 첫 선택에서는 순아래 선택 표시가 있어도 영문이 나온 경우가 있었다.
기본 두벌식으로 바꾼 뒤 순아래를 다시 선택하자 같은 설치 파일로 한글 입력이 됐다.
웹 입력 소스 목록이 한 번 비어 있던 경우도 시험 버튼을 다시 눌러 정상 선택을 확인했다.
선택 표시나 설치 성공만으로 실제 입력이 된다고 판단하지 않았다.

## 남은 문제: 빠른 입력 중 공백 순서

아래는 재조회 수정만 적용한 시점의 기록이다. 뒤이은
[공백 순서 수정 검증](INPUT-VERIFICATION-SPACE-ORDER.md)에서 수정·설치와 반복 시험 결과를 확인할 수 있다.

Vim 삽입 모드에서 공백을 포함한 키를 빠르게 연속 전송하면 다음 문제가 간헐적으로 나왔다.

- 기대: `까 각 과 예`
- 새 빌드에서 관찰: `까 각 과ㅇ ㅖ`, 또는 공백이 뒤로 밀린 `까각 과 예`.
- 이전 빌드를 다시 설치해 같은 시험을 했을 때도 `까 각과 예`, `까ㄱ ㅏㄱ 과 예`, `까 각ㄱ ㅘ 예`가 나왔다.
- 새 빌드의 한 실패 기록에서는 다음 `ㅇ`의 `insertText`가 공백의 `keydown`과 공백 삽입보다 먼저 나타났다.

새 빌드에서 전체 예문을 입력한 Vim 시험 6회 중 2회, 이전 빌드에서 입력 소스 연결 뒤
진행한 14회 중 3회에 공백 위치 또는 조합 오류를 관찰했다. 설치 직후 영문이 나온
첫 시험은 이 수에서 제외했다. 표본과 시점이 달라 오타율이나 개선율 비교로 쓸 수 없다.

이 문제는 이전 빌드에도 있었고 이번 재조회 수정으로 해결하지 못했다.
기본 입력·삭제·표시·Enter 확인 통과와, 빠른 연속 입력의 정확성은 구분해야 한다.
실제 사용 앱의 오타 원인이 모두 밝혀졌거나 해결됐다고 볼 수 없다.

비교 후 새 빌드를 다시 설치했고 실행 경로·해시·실제 입력을 확인했다.
시험창은 종료했다. 다른 작업 앱의 문서를 건드리거나 앱을 재시작하지 않았다.

고정 예문 기록은 추적하지 않는 `tmp/live-direct-retry-check/`의
`new-build.jsonl`, `old-build.jsonl`, `final-installed.jsonl`에 보관했다.
