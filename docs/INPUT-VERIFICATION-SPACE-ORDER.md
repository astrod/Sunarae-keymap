# 공백 순서 수정 검증 — 2026-10-06

## 변경과 설치

직접 조합 중인 한글 바로 뒤의 일반 Space를 한글과 같은 `insertText` 경로로 넣고
키를 처리 완료로 돌려준다. 공백이 다음 자음보다 늦게 들어가는 일을 막는다.
삽입 전에는 같은 문서·커서·글자인지 확인한다.

Enter, Tab, Escape, 수정키가 붙은 Space와 조합이 없는 Space는 앱에 전달한다.
문서 확인이 실패하거나 조합 표시를 쓰는 클라이언트에서도 기존 처리를 유지한다.
Caps Lock은 일반 Space 처리에 영향을 주지 않는다.

이 빌드는 앞선 [직접 교체 재조회 수정](INPUT-VERIFICATION-DIRECT-RETRY.md)을 포함한다.
버전 표시는 `0.5.1 (20)`인 개발 빌드이며 정식 배포는 하지 않았다.

  `a5ce752b631f705b94b47ded987c2b068a047df5ed68fbf860110309f402ed2c`

- 설치 경로에서 실행 중인 프로세스를 확인했고, 시험창 종료 후 순아래를 다시 선택했다.

## 실제 키 입력

사용자 허락을 받아 별도 시험창에서 고정 예문을 키로 입력했다. 붙여넣기를 쓰지 않았다.

- 네이티브: `까 각 과 예`와 Enter 줄바꿈 확인. 조합 표시 호출이 없고,
  마지막 선택 길이와 조합 범위 길이는 0이었다.
- 일반 웹 20회, Vim 삽입 모드 20회: `rkk rkr rhk dul`과 Return을 빠르게 전송했다.
  40회 모두 `- 까 각 과 예\n- `로 목록이 이어졌다. 별도 첫 연결 확인도 통과했다.
- 위 반복 시험의 공백 120개 모두 다음 자음 앞에 들어갔다.
  조합 이벤트는 0개였고, Enter 40개 모두 `keyCode=13`, `isComposing=false`,
  편집기 `composing=false`였다.
- 일반 웹·Vim 삽입 모드에서 `ㄹ` 다섯 개를 연속 삭제한 직후 `rkk → 까`,
  Backspace로 `가`를 확인했다. 마지막 글자가 선택된 것처럼 보이지 않았다.
- Vim 일반 모드에서 Space는 문서를 바꾸지 않고 커서를 0에서 1로 옮겼다.
- 웹 첫 연결에서 입력 소스 목록이 한 번 비었으나, 다시 선택한 뒤 실제 한글 입력이 됐다.

앞서 재현한 공백 순서 오류는 이 시험에서 나오지 않았다. 모든 앱·모든 오타의 해결을
뜻하지는 않는다. 연속 공백, 문장 부호 등 조합 밖의 키는 기존처럼 앱이 처리한다.
사용자의 기존 작업 앱 문서를 이 시험에 쓰거나 앱을 재시작하지 않았다.

고정 예문 기록과 집계는 추적하지 않는 `tmp/live-space-order-check/`의
`installed-build.jsonl`, `summary.json`에 보관했다.
