# 실제 입력 처리 시간 측정

두꺼비 0.2.4의 조합 계산뿐 아니라 InputMethodKit 클라이언트와 통신하는 시간을 측정했다. 키 처리 144건에서 평균 4.557ms, 최대 18.826ms를 확인했다. 측정한 키 처리 시간의 합계 중 약 99.4%가 앱 조회·글자 전달 API 호출 안에서 걸렸다. 조합 계산의 평균은 0.006ms였다.

실제 처리 시간에 편차가 있다는 근거다. 사용자가 느낀 밀림 전체의 원인을 확정하거나 기본 두벌식보다 느리다고 입증한 결과는 아니다.

## 방법

- 배포 소스는 그대로 두고 `build/latency-2026-09-07/Sources`에 측정용 복사본을 만들었다.
- 원래와 같은 최적화 설정으로 빌드했다. 앱 권한과 한글 입력 규칙을 바꾸지 않았다.
- InputController가 keyDown을 받았을 때 시작하고 InputSession 처리 반환까지 단조 증가 시계로 쟀다.
- 앱 선택 범위, 기존 글자 조회, 지원 기능 조회, 글자 삽입, marked text 조회·설정 호출을 각각 쟀다. 한글 조합과 Backspace 계산도 따로 쟀다.
- 각 단계 시간은 해당 키 처리 시간 안에 포함된다. 단계별 백분위수를 서로 더하면 전체 백분위수가 되지 않는다.
- 입력한 글자, 키 코드, 글자 범위, 앱 식별자는 저장하지 않았다. 시간 표본을 메모리에 모으고 통계만 10초마다 로컬 파일로 저장했다.
- 사용자에게 평소 입력창에서 한글을 입력해 달라고 요청했다. 첫 입력부터 120초 동안 수집했고 144건을 얻었다. 이 중 텍스트 쓰기 호출이 있는 키 처리는 96건이다.
- 자동 검사창의 고정 입력은 ASCII로 남았고 시스템 두꺼비 경로를 통과하지 못했다. 그 결과를 한글 입력 지연 측정치로 사용하지 않았다.
- 평균과 백분위수에 측정 코드의 비용도 포함된다. 측정 종료 후 일반 0.2.4 실행 파일로 복원했다.

## 결과

단위는 ms다. P95는 표본의 95%가 그 값 이하라는 뜻이다. API 단계는 해당 호출이 있었던 키 처리만 집계했다. 동일 키에서 같은 API를 여러 번 호출했다면 합산했다.

| 구간 | 표본 수 | 평균 | P50 | P95 | 최대 |
|---|---:|---:|---:|---:|---:|
| 전체 키 처리 | 144 | 4.557 | 3.275 | 15.093 | 18.826 |
| 텍스트 쓰기가 있는 키 처리 | 96 | 6.660 | 4.272 | 15.884 | 18.826 |
| 앱 API 호출 합계, 전체 키 기준 | 144 | 4.530 | 3.242 | 15.062 | 18.791 |
| 조합·Backspace 계산 | 137 | 0.006 | 0.003 | 0.014 | 0.117 |
| 글자 전달 호출 | 96 | 4.940 | 1.668 | 14.963 | 18.112 |
| 기존 글자 조회 | 73 | 1.834 | 0.653 | 5.071 | 9.786 |
| 커서·선택 범위 조회 | 100 | 0.393 | 0.318 | 0.739 | 2.556 |
| 문서 접근 지원 조회 | 26 | 0.192 | 0.194 | 0.256 | 0.265 |

전체 키 처리의 P99는 18.738ms였다. 16.7ms를 넘은 키 처리는 4건이고, 33.3ms를 넘은 것은 없었다. 표본이 144건이라 느린 쪽 1%의 추정은 안정적이지 않다. 이 한 번의 측정으로 더 긴 지연이 없다고 결론낼 수 없다.

이번 측정에서 marked text 조회·설정 호출은 없었다. 글자 전달은 일반 텍스트 경로를 사용했다.

## 해석과 한계

조합 계산보다 앱 API 호출이 측정 시간의 대부분을 차지했다. 특히 글자 전달 호출에서 가장 긴 시간을 확인했다. API 호출 시간에는 프로세스 사이의 통신, 앱의 응답을 기다리는 시간, 그동안의 실행 지연이 함께 들어갈 수 있다. 지금 자료만으로 그 안을 더 나눌 수는 없다.

키보드 스캔·무선 전송·macOS가 입력기로 이벤트를 전달하기 전의 대기, API가 반환한 뒤 앱이 비동기로 처리하는 시간, 화면에 실제 픽셀이 뜨는 시간은 측정하지 않았다. 이 수치를 키를 물리적으로 누른 순간부터 화면 표시까지의 시간으로 읽으면 안 된다.

앱 식별자를 수집하지 않아 이 자료만으로 앱별 차이를 구분할 수 없다. 기본 두벌식을 같은 앱과 같은 입력 조건으로 측정한 비교군도 없다. 따라서 현재 자료는 두꺼비의 실제 처리 구간에 수 ms에서 약 19ms의 시간이 걸렸음을 보여준다.

이전 조합 엔진 반복 측정은 짧은 예문을 쉬지 않고 돌린 계산 평균이다. 이번 측정은 앱 안의 실제 입력 호출이므로 실행 간격과 초기 실행 비용 등이 다르다. 이번 조합 평균 0.006ms와 이전 약 0.0001~0.0002ms를 버전 간 속도 차이로 해석하지 않는다.

입력 누락 방지를 위해 넣은 커서·문자열 확인을 근거 없이 제거하지 않는다. 성능을 더 조사한다면 우선 글자 전달 호출이 길어지는 조건을 확인하고, 같은 앱에서 기본 두벌식과 비교해야 한다.
