# dukkeobi의 SilverBullet 입력 지원 계획

2026-09-06. 이번 작업은 조사와 계획 작성이다. 앱 코드와 설치본은 바꾸지 않았다.

목표는 두겹이 조합과 `;` 대체 시프트를 유지하면서, SilverBullet에서 한글을 친 직후 Enter를 한 번 누르면 기본 두벌식과 같이 다음 글머리표로 이동하게 하는 것이다. 키보드 모델이나 펌웨어에는 의존하지 않는다.

현재 사용자는 0.2.0이 예상대로 동작하지 않는다고 보고했다. 구체적인 증상이 기존 Enter 문제인지, 글자 조합 자체의 문제인지 아직 구분되지 않았다. 따라서 아래 원인 후보 중 하나를 확정 원인으로 주장하지 않는다.

**이번에 확인한 사실**

| 항목 | 확인 결과 | 판단 범위 |
|---|---|---|
| 설치·실행 | 설치본은 0.2.0이며 dist 실행 파일과 SHA-256이 같다. 실행 중인 프로세스는 설치 경로를 사용하고 바이너리 수정 시각 이후에 시작했다. | 단순히 예전 설치본이 남아 있는 경우를 뒷받침하는 증거는 없다. |
| 새 전달 방식의 선택 | `InputSession.update`는 유효한 선택 범위와 길이 0인 문자열 조회를 요구한다. 실패하면 `.marked`를 선택한다. | SilverBullet에서 어느 분기를 쓰는지 아직 측정하지 않았다. 새 버전도 예전 조합 방식을 쓸 수 있다. |
| 조합 유지 | `reconcile`은 클라이언트 객체, 커서, 기존 글자 중 하나라도 예상과 다르면 조합을 즉시 초기화한다. | 읽은 값이 늦게 갱신되거나 객체 식별이 바뀐다면 조합이 끊길 가능성이 있다. 실제 발생 여부는 미확인이다. |
| 범위 교체 | `insertText` 호출 후 다음 교체 범위를 계산한다. 교체가 실제로 적용됐는지 그 호출 안에서 확인하지 않는다. | 앱이 교체 범위를 무시하거나 다른 위치에 넣는 경우를 현재 검사로 보장할 수 없다. |
| 기존 검사 | `Tests/main.swift`는 NSTextView를 사용하는 자체 TextClient를 직접 호출한다. Enter 검사는 `false` 반환을 확인하고 테스트가 직접 `\n- `를 넣는다. | 11,910개 통과는 한글 조합과 해당 편집 코드의 결과다. SilverBullet의 Enter 처리나 목록 생성 검사는 아니다. |
| 자동 UI 입력 | 앞선 시도는 한글 입력 소스를 통한 조합을 확인하지 못했다. | 영문이 들어온 이유도 단정하지 않는다. 입력 소스 적용 문제인지, 자동 이벤트 경로 문제인지 먼저 확인해야 한다. |

**기본 두벌식과의 비교에서 바로잡을 점**

WebKit 개발자는 macOS 기본 한글 입력기가 별도의 inline composition 세션을 만들지 않는다고 설명했다. 이는 전달 방식의 차이를 뒷받침하지만, `setMarkedText`를 `insertText`로 바꾸기만 하면 모든 편집기에서 같은 동작을 얻는다는 근거는 아니다. Apple 입력기의 정확한 호출 순서와 입력기 전환·커서 조회 동작은 이 Mac에서 아직 기록하지 않았다.

환경은 macOS 26.6.2 (25G83), WebKit 21624.5.1.11.3, SilverBullet+ 앱 2.10.0이다. SilverBullet이 실제로 로드한 웹 클라이언트와 CodeMirror의 정확한 빌드는 별도로 확인해야 한다. 앱의 버전과 웹 클라이언트 버전이 같다고 가정하지 않는다.

이전에 참고한 WebKit main과 버전 번호가 대응하는 공개 태그 `WebKit-7624.5.1.11.3`을 비교했다. 공개 태그가 설치 바이너리와 완전히 같다고 확인한 것은 아니다.

- main에는 대기 중인 `insertText`의 교체 범위를 보존하고, 커서·문자열 조회에 아직 적용하지 않은 삽입을 반영하는 처리가 있다.
- 위 공개 태그의 `insertText`는 명령 수집 분기에서 교체 범위가 없다고 가정하고 범위를 담지 않은 명령을 만든다. 커서·문자열 조회에도 main과 같은 삽입 보정이 없다.
- 이 명령 수집 분기는 조건부다. SilverBullet에서 해당 분기를 실제로 실행했는지는 확인하지 않았으므로 이를 직접 원인으로 단정할 수 없다.
- main에 있는 특정 기본 입력기 ID에 대한 분기를 이 Mac에도 적용되는 설명으로 사용하지 않는다.

CodeMirror의 공개 입력 처리 코드에는 조합 중이거나 Safari에서 조합 종료 직후인 경우 키 처리를 건너뛰는 로직이 있다. 그러나 이 Mac의 SilverBullet에서 실제 Enter가 그 조건에 걸렸는지는 아직 측정하지 않았다.

**작업 순서와 단계별 완료 조건**

1. **기본 두벌식을 기준으로 실제 호출을 기록한다.**

   작은 로컬 검사 앱에 일반 NSTextView와 WKWebView 편집 영역을 둔다. NSTextView 쪽에서는 공개 텍스트 입력 API를 통해 `insertText`, `setMarkedText`, `unmarkText`, 선택 범위·문자열 조회, Enter 처리 순서를 기록한다. WKWebView 쪽에서는 `keydown`, `beforeinput`, `input`, `compositionstart/update/end`, 선택 변경을 기록한다. `isComposing`, `inputType`, Enter의 처리 여부와 최종 문서 내용을 함께 확인한다. WKWebView의 비공개 클래스나 메서드에 의존하지 않는다.

   같은 고정 예문을 macOS 기본 두벌식과 dukkeobi에 입력한다. 먼저 `가`, `각`, `어렵다`, `- 어렵다`를 사용한다. 마지막 글자 직후 Enter와 잠시 기다린 뒤 Enter를 나누어 본다. 두겹이만의 규칙은 이 비교 다음에 검사한다.

   실제 키 입력이 선택한 입력기를 거쳤다는 증거가 있어야 비교 결과로 인정한다. 자동 입력이 영문을 넣거나 입력기 콜백에 도달하지 않으면 그 자동화는 검증 수단으로 쓰지 않는다. 필요한 경우 이 단계에서만 사용자가 두 입력기로 짧은 예문을 직접 치는 절차를 둔다.

   완료 조건: 동일한 예문에서 기본 두벌식과 dukkeobi가 처음 달라지는 호출 또는 웹 이벤트를 지목할 수 있다.

2. **dukkeobi의 실패 분기를 구분한다.**

   검사 빌드에 한정해 전달 모드, 모드 선택 이유, 선택·교체 범위, 조회 성공 여부, 문자열 일치 여부, 조합 초기화 이유, Enter 처리 반환값을 기록한다. 클라이언트 식별자가 키 사이에서 유지되는지도 확인한다. 기록은 고정 예문을 입력하는 검사 세션으로 제한하고, 일반 문서의 입력 내용이나 키 기록은 저장하지 않는다. 외부 전송과 새 입력 감시 권한은 추가하지 않는다.

   먼저 로컬 WKWebView에서 원인을 분리한 뒤, SilverBullet이 사용하는 CodeMirror 버전과 목록·Vim 설정을 맞춘 검사 환경에서 확인한다. 마지막으로 설치된 SilverBullet의 별도 테스트 문서에서 확인한다. 설치된 앱에서 이벤트 관찰이 불가능하면 검사 환경의 기록과 실제 앱의 결과를 구분해 보고한다.

   완료 조건: 예전 방식으로 돌아가는 문제, 잘못된 조합 초기화, 범위 교체 실패, 편집기의 Enter 처리 중 어디에서 실패하는지 증거로 구분한다.

3. **확인한 원인에 맞춰 전달 부분만 수정한다.**

   조합 엔진과 두겹이 배열은 유지한다. 기능 지원 여부를 길이 0인 조회 한 번으로 판단해도 되는지 검사 결과에 따라 고친다. 조회가 늦게 반영되는 문제라면 실제 커서 이동과 구분할 근거를 만든다. 범위가 검증되지 않은 상태에서 이전 글자를 무조건 덮어쓰도록 안전 검사를 없애지는 않는다.

   직접 교체가 동작하는 경로에서는 Enter에 추가 삽입이나 marked text 종료가 필요 없도록 유지한다. marked text 경로에서는 조합 종료와 Enter가 앱에 도달하는 순서를 따로 검사한다. `false` 반환만으로 편집기가 Enter를 처리했다고 간주하지 않는다.

   공개 API와 현재 WebKit의 동작 때문에 직접 교체를 안정적으로 구현할 수 없다면, 그 제한을 별도 결과로 보고한다. 앱 쪽 수정이나 다른 WebKit 버전이 필요한 경우를 dukkeobi만의 수정으로 해결했다고 표현하지 않는다. 단순 대기 시간 추가나 Enter 재전송으로 통과한 것처럼 만들지 않는다.

   완료 조건: 실패 원인과 대응하는 변경을 설명하고, 수정 전 실패·수정 후 성공을 같은 검사에서 확인할 수 있다.

4. **실제 동작을 통과 기준으로 삼은 뒤 업데이트한다.**

   - SilverBullet에서 `- 어렵다` 직후 Enter 한 번으로 다음 목록 항목이 생긴다. 마지막 글자와 줄바꿈은 각각 한 번만 반영된다.
   - 빠르게 이어 친 경우와 잠시 멈춘 경우 모두 같은 결과를 얻는다. 정상 목록 입력과 사용자의 Vim 입력 모드에서 확인한다.
   - `홈로우`, `입력`, `맑`, `까`, `걔`의 조합과 받침·대체 시프트 Backspace가 유지된다.
   - 커서 이동, 선택 영역 교체, 이모지 뒤 입력, 입력기 전환, Command 단축키, Undo에서 문서가 손상되거나 글자가 중복되지 않는다.
   - 일반 NSTextView와 WKWebView에서 기본 두벌식과 결과를 비교하고 기존 조합 검사도 통과한다. 확인하지 않은 다른 앱까지 지원한다고 확대하지 않는다.

   이 조건을 만족한 결과와 남은 제한을 보고한 뒤 사용 중인 설치본에 반영한다. 수정 전 앱을 보관해 복원할 수 있게 한다. 검사 수만 늘리거나 테스트에서 글머리표를 직접 만들어 성공으로 처리하지 않는다.

**이번 조사 결과**

직접 원인은 아직 미확정이다. 0.2.0에는 실제 앱에서 확인하지 않은 전달 모드 선택과 조합 유지 조건이 있으며, 이전 조사는 최신 WebKit 소스와 이 Mac의 동작을 구분하는 데 부족했다. 다음 작업의 첫 결과물은 새 설치본이 아니라 두 입력기의 비교 기록과 실패 분기 판정이어야 한다.
